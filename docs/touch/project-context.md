> Документ для внешней оценки (передаётся GPT-5.6 SOL). Цель — дать читателю,
> который никогда не видел проект, весь необходимый контекст: что такое Sens,
> как он устроен, какие правила и ограничения действуют, и почему следующие
> решения (см. `touch-1.4.0-plan.md`) принимаются именно так.
>
> Дата: 2026-08-13. Актуальная версия: **1.3.8** (released).

---

## 1. Что такое Sens

Sens — это **Windows MCP-рантайм**, который даёт текстовым LLM-моделям
(DeepSeek и другие модели без нативного зрения) локальные «глаза» и «уши»:
структурированные визуальные и аудио-доказательства вместо описаний
«на глазок».

Один абзац: Sens — десктоп-приложение (Tauri 2 + Rust + React), внутри которого
живёт Rust-брокер (`sens-broker`), который супервизирует Python/Node-воркеров
(`sidecars/`). Всё это публикуется наружу как **MCP-сервер** (`sens-mcp`) с
тулами вида `sens_see`, `sens_read`, `sens_hear`, `sens_web_review` и т.д.
Любая текстовая модель в любом MCP-совместимом хосте (ZCode, Codex, Cline,
Qwen Code, Claude Code и т.п.) подключает Sens и получает «чувства».

Принципиальная позиция проекта:

- **Детерминированное измерение первично, VLM вторичен.** OCR, геометрия,
  цвета, сетка, сравнение изображений — это `measured` (измеренное).
  Семантический VLM (маленькая локальная модель) используется только там, где
  интерпретация реально добавляет пользы — это `inferred` (выведенное).
  Модель никогда не выдаёт догадку за факт.
- **Всё локально и на CPU.** Vision-инференс работает только на CPU с бюджетом
  RAM ≤ 2 ГБ на модель. GPU не используется (у автора есть RTX 4070 SUPER, но
  это осознанный архитектурный выбор: цель — работать на любом Windows-ПК).
- **Брокер — единственный владелец.** Все capability-воркеры и изменяемое
  состояние рантайма принадлежат Rust-брокеру. Воркеры stateless.
- **Sens — «чувства», а не «руки».** Sens не редактирует файлы пользователя,
  не выполняет команды в его репозитории, не лезет в буфер обмена. Он
  *наблюдает и измеряет* и возвращает evidence. До 1.4.0 (см. план Touch) —
  это строго так. Touch добавляет ограниченное «осязание» с жёсткими
  песочницами.

## 2. Ниша и конкурентное положение

Ресёрч 2026-08-12 (`.omx/research/summary-vision-competitors.md`) по вопросу
«как текстовые LLM получают зрение»:

| Паттерн | Примеры | Локально? | Оценка |
|---|---|---|---|
| MCP-мост «текст-LLM → внешняя VLM» | moondream-mcp, minicpm-vision-mcp, LocalEyes, llm-eyes | да (CPU) | ближайшие аналоги, но все делают «описание картинки» без измерений |
| Облачные vision API через MCP | luma-mcp, deepseek-eyes (ModelScope) | нет | не наш паттерн |
| Нативные мультимодальные веса | SmolVLM2, Qwen2.5-VL и др. | да | используются как L5-слой внутри Sens |

Вывод ресёрча: ниша «текст-LLM + локальный CPU-глаз» почти пуста, а у всех
конкурентов отсутствует главное — **замкнутый цикл верификации**:
`sens_see` (посмотреть) → `sens_review`/`sens_compare` (сравнить кандидата с
эталоном по метрике, получить repairHints — точечные подсказки, что чинить).
Конкуренты описывают картинку; Sens измеряет и даёт цикл исправлений с
числовой метрикой совпадения.

Этот же «не верь модели на слово» подход предполагается перенести в новое
чувство — Осязание (Touch): воркер-модель может предложить claims, но Sens
**детерминированно проверяет** их (файл существует, строка совпадает, URL
докачан и содержит цитату). «Единственный MCP, который не верит модели на
слово».

## 4. Архитектура

```text
┌──────────────────────────────────────────────────────────────┐
│  Внешний хост (ZCode / Codex / Cline / любая текстовая LLM)   │
│  ── подключается как MCP-клиент                                │
└───────────────────────────┬──────────────────────────────────┘
                            │ MCP (stdio), JSON-RPC 2.0
┌───────────────────────────▼──────────────────────────────────┐
│  sens-mcp  (Rust crate)                                       │
│  ─ публикует тулы sens_*; stdout чистый, диагностика в stderr │
└───────────────────────────┬──────────────────────────────────┘
                            │ внутренний вызов
┌───────────────────────────▼──────────────────────────────────┐
│  sens-broker  (Rust crate)                                    │
│  ─ ЕДИНСТВЕННЫЙ владелец воркеров и mutable runtime state      │
│  ─ capability-координаторы: Sight, Hearing, (1.4.0: Touch)    │
│  ─ approval/лимиты/отмена/кэш/сессии                          │
└──────┬──────────────────────────┬────────────────────────────┘
       │ stdin/stdout (JSONL)      │ stdin/stdout (JSONL)
┌──────▼──────────┐        ┌───────▼──────────┐
│ sight-worker.py │        │ hearing-worker.py│  (+ eye-worker.mjs,
│ (Python, CPU)   │        │ (Python, CPU)    │    speech/ каталог)
└─────────────────┘        └──────────────────┘
       │                            │
       ▼                            ▼
  локальные модели           локальные ASR (Qwen3-ASR,
  (Qwen3-VL-2B,              GigaAM, Whisper) ИЛИ удалённый
  SmolVLM2-2.2B ...)         OpenRouter по ключу пользователя
```

Ключевые факты об архитектуре:

- **5 Rust-крейтов**: `sens-broker` (владелец состояния), `sens-mcp` (MCP
  поверх), `sens-connect`, `sens-core`, `sens-protocol` (общие типы).
- **Desktop**: `apps/desktop-ui` — Tauri 2 + React (Vite). Окна main и tray,
  настройки (тема, язык, пакет vision), first-run setup Sight, индикация
  статусов capability. UI на английском.
- **Sidecars** (`D:\Sens\sidecars\` при разработке): `sight-worker.py`
  (зрение, Python + opencv/ultralytics/onnx), `hearing-worker.py` (слух,
  Python, ASR), `eye-worker.mjs` (Node.js, ранее — облачный Eye), `speech/`
  (материалы речевого рантайма), `rapidocr-cyrillic.yaml` (OCR-модель).
- **Деплой воркеров**: при установке sidecars копируются в
  `AppData\Local\Sens\sidecars\`; MCP-тулы запускают воркеров именно оттуда,
  а не из репозитория. Обновление воркера = `cp` + PowerShell-скрипт убивает
  старые процессы. Поиск воркера: env `SENS_SIDECARS_ROOT` → рядом с
  исполняемым файлом (`sidecars/`) → системный python. Упакованный python
  живёт в `runtime/python/python.exe` внутри установки.
- **Протокол воркера**: JSONL по stdin/stdout; воркер stateless; на каждый
  запрос отвечает результатом в общей обёртке (envelope).

## 5. Envelope и честность данных (ключевой инвариант)

Правило из `AGENTS.md`, обязательное для всех capability:

> Каждый результат capability использует общий request/result envelope и
> различает **observed** (наблюдаемое), **measured** (измеренное) и **inferred**
> (выведенное) данные.

Это значит:

- Модель (VLM, ASR) никогда не диктует «факты»: её вывод всегда помечен как
  `inferred`, с уверенностью и методом.
- Детерминированные измерения (OCR, геометрия, цвета, сравнение пикселей,
  длительности) помечаются как `measured`.
- То, что система реально захватила (скриншот, файл, аудио), — `observed`.
- Когда модель ссылается на evidence (например, «в файле X на строке Y...»),
  Sens может **проверить claim детерминированно** — это основа нового чувства
  Touch.

Следствие для разработки: запрещено «притворяться». Нельзя показывать баланс,
которого нет, нельзя показывать результат проверки, которая не выполнялась,
нельзя маркировать догадку как факт. Визуальные состояния UI должны честно
отражать состояние системы.

## 6. Чувства (capabilities)

### 6.1 Зрение — Sight (Eye)

Тулы (префикс `sens_`):

- `sens_see` — основной анализ изображения: детерминированные слои L0–L5 +
  bounded zoom-регионы, возвращает структурированный документ (тексты, блоки,
  элементы, цвета, координаты).
- `sens_read` — OCR (текст, числа, таблицы, даты, валюта) с уверенностью и
  методом.
- `sens_inspect` / `sens_locate` / `sens_zoom` — повторный анализ точных
  source-pixel регионов (reversible к оригиналу).
- `sens_ask` — вопрос к локальному CPU VLM (только там, где нужно
  семантическое понимание).
- `sens_compare` — строгое сравнение кандидата с эталоном (fit=strict,
  точные размеры, без ресемплинга).
- `sens_review` — композиционный гейт: визуальное совпадение + живые
  selectable DOM-тексты + семантические контролы + CSS-геометрия +
  доступность + аудит raster-политики; возвращает repairHints с
  source-pixel координатами.
- `sens_capture` — захват явного http(s) URL (bounded browser).
- `sens_web_start` / `sens_web_review` — broker-owned URL reconstruction
  сессии (1.3.8): источник замораживается один раз, каждый репаир
  переснимается заново, завершение — только по broker-issued receipt.

Пайплайн Sight (слои):

- L0–L4 — детерминированные измерения: цвета, сетка/координаты, детекция
  объектов (yolov8n), сцена, текстуры. Без нейросетей или с лёгкими ONNX.
- L5 — семантический VLM (GGUF, CPU-only, бюджет RAM ≤ 2 ГБ на модель):
  - `lite` — Qwen3-VL-2B (Q4);
  - `quality` — SmolVLM2-2.2B (Q4) — дефолт quality;
  - `quality_large` — Qwen2.5-VL-3B (опт-ин, не проходил бенчмарк).
- Вся пайплайн-механика: кэш (content-addressed), замеры, bounded
  focus-регионы, motion (анимации CSS через frame-diff).

Review-цикл (моат): `sens_see` → реализация → `sens_review` с метрикой
совпадения и repairHints → ограниченный репаир → повторный review. Завершение
только при visualPass + webPass + canComplete + пустые blockingReasons.

### 6.2 Слух — Hearing (Speech)

- `sens_hear` — транскрипция локального аудио/видео файла: таймстампы,
  сегменты, автоматический язык. Модели: Qwen3-ASR (локальный дефолт, CPU),
  GigaAM, Whisper; или удалённо через OpenRouter (по ключу пользователя):
  `gpt-4o-transcribe` (json-only) и `grok-stt-1.0` (с сегментами).
- `sens_watch` — анализ локального видеофайла (кадры + вопросы).
- `sens_fetch` — докачка видео URL в локальный кэш (например YouTube) для
  последующего `sens_hear`/`sens_watch`.
- Известный баг (урок): `sens_watch`/`sens_fetch` долго не работали, потому
  что не были зарегистрированы в capability-манифестах. **Урок: новые тулы
  регистрируются в манифестах сразу.**

Правила слуха: агентная транскрипция **не пишет** в буфер обмена, не вставляет
текст, не сохраняет историю — только если пользовательский сценарий явно это
запросил.

### 6.3 (1.4.0) Осязание — Touch

Описано в `touch-1.4.0-plan.md`. Коротко: MCP-тулы делегирования подзадач
дешёвым воркер-моделям (OpenRouter/DeepSeek по ключу пользователя) с ролями,
бюджетами, изоляцией контекста, структурированными результатами и
детерминированной проверкой claims.

## 7. Конфигурация и ключи

- Конфиг: `config.json` в корне Eye/установки (`eye_root/config.json`).
  Пример известного поля: `vision.visionPack` = `lite | quality |
  quality_large` — читается брокером (Rust) и передаётся воркеру.
- **Паттерн ключа Eye**: пользователь сам вписывает API-ключ провайдера в
  `config.json`; воркер использует его только по прямому назначению. Ключи
  никогда не попадают в код, логи, аргументы команд, activity-записи или
  диагностику. Этот же паттерн планируется для Touch.
- Проверено: в коде и установке Sens нет вшитых API-ключей; воркеры по
  умолчанию не имеют сети; единственная сеть — Eye (и слух-remote) с ключом
  пользователя из config.json.

## 8. Ограничения и инварианты (правила разработки)

Из `AGENTS.md` (обязательные):

1. Rust-брокер — единственный владелец capability-воркеров и изменяемого
   состояния рантайма.
2. stdout в `sens-mcp` чистый: только протокол. Диагностика — в stderr.
3. Никаких API-ключей и IPC-секретов в аргументах команд, логах,
   activity-записях, диагностических экспортах.
4. Eye и Speech — brownfield-воркеры: сохранять их публичное поведение и
   тесты перед рефакторингом внутренностей.
5. Агентная аудио-транскрипция не пишет в буфер обмена/историю без явного
   пользовательского сценария.
6. Модельно-управляемые микрофон и захват экрана требуют явного видимого
   согласия и выходят за рамки Sens 1.x.
7. Каждый результат — в общем envelope, различающем observed/measured/inferred.
8. Перед завершением Rust-слайса: `cargo fmt --check`, `cargo clippy
   --workspace --all-targets -- -D warnings`, `cargo test --workspace`.
9. Скриншоты из чата декодируются скриптом `scripts/extract-chat-images.mjs`
   в `qa/incoming/` и разбираются Sens Eye-тулами, а не глазом ассистента.

Прочие факты среды:

- Пользовательский экран: 2048×1152 (скриншоты/обои готовятся под него).
- Машина: Windows 10/11 x64, 16 ГБ RAM минимум (рекомендуется 32), CPU ≥ 6
  ядер; GPU RTX 4070 SUPER есть, но Sens vision сознательно CPU-only.
- Python не на PATH в Git Bash; виртуальное окружение с cv2 — в
  `D:\Speech\.venv` (наследие).

## 11. Что Sens НЕ делает (границы продукта)

- Не инферит на GPU (только CPU).
- Не хранит данные пользователя в облаке; нет телеметрии (локальный
  `ledger.json` — диагностика).
- Не управляет файлами/командами пользователя (до Touch; Touch — только
  песочницы и read-only).
- Не захватывает микрофон/экран без явного согласия.
- Не обходит DRM, не импортирует куки браузера, не работает с
  приватными/авторизованными сайтами.
- Не выдаёт выдуманные метрики, балансы, статусы.

## 13. Словарь терминов (для внешнего читателя)

| Термин | Значение |
|---|---|
| MCP | Model Context Protocol — открытый протокол «инструментов» для LLM: сервер публикует тулы, модель вызывает их по описанию. |
| capability | «Чувство» Sens: Sight, Hearing, Touch. Координатор в брокере + воркер + набор MCP-тулов. |
| worker (sidecar) | Отдельный процесс-воркер (Python/Node), супервизируемый брокером; stateless, JSONL по stdin/stdout. |
| envelope | Общая обёртка запроса/результата всех capability; различает observed/measured/inferred. |
| observed / measured / inferred | Наблюдаемое (захват) / измеренное (детерминированный расчёт) / выведенное (модельное заключение). |
| repairHints | Точечные подсказки для исправления кандидата (координаты, типы правок) от `sens_review`. |
